**What happened**

- Built `scripts/mcp-lab-fixture.mjs` — named arrangements (`scenario-g`, `scenario-g2`, `scenario-k`) applied to
  the throwaway lab AFTER seeding, behind the seeder's `*-lab.db` guard. The shared seed stays untouched.
- **Scenario G re-run clean, twice.** Arrangement 1: confusion pair in the batch because it is DUE (not via
  `focusPatterns`), one pattern, new-item and vocab quotas zeroed. Treatment 3/3 produced the same frame;
  criterion 1 (the distinction decides the answer) 0/3; control produced three unrelated frames. Not acted on yet,
  because that pair is two near-synonyms and the criterion may be unsatisfiable for it. Arrangement 2 used a pair
  whose confusion INVERTS the meaning, on a pattern with no card (a card's `usage`+pitfall prints on the item row
  and would leak the hint into control). Treatment 0/3 again — and the ONLY distinction-decisive sentence in all
  twelve trials came from a CONTROL trial.
- **Fired the pre-written cut.** The learner-model digest left `get_due_items` and now renders once per session on
  `get_stats`, as a Claude-facing note after the verbatim block. Took `computeDossier` off the per-exercise path
  with it. Scenario H retired — it guarded the digest naming a pattern outside the batch, and there is no batch
  context left. Gates: `render.test.ts` asserts the sheet has no `LEARNER MODEL`; `dossier.test.ts` asserts the
  wording aims at a session, not an exercise.
- **Scenario K measured for the first time, in SQL.** A subagent drove five complete real turns through the lab
  (`get_due_items` → `stage_sentence` → answer → `submit_review`, real ids) playing both tutor and an unremarkable
  learner. `SELECT COUNT(*) FROM LearnerNote` → **0**, with 5 GRADED sentences and 14 new `ReviewLog` rows proving
  the turns happened. Then a SIXTH turn built to trigger a note (the learner talks themselves out of an answer that
  was already right) — also zero. The observation went into the throwaway per-turn `feedback` instead.
- Diagnosed that as the same shape as the previous day's ratchet starvation: `learnerNote` was described only as
  "OPTIONAL, and rare", with no positive trigger. Added a named trigger list while keeping "most turns, send
  nothing" — and re-measured **0/3. The fix did not land.** One trial's `feedback` narrated the trigger nearly
  word for word and still sent no note. Remaining hypothesis is PLACEMENT (a nested `.describe()` vs the
  always-loaded protocol, which is where the ratchet fix worked), so the clause also went into
  `PRACTICE_PROTOCOL` step 6 — **and there it fired 3/3, on the same words**. (First attempt at that
  measurement lost all three trials to an API session limit; re-run after the reset.)
- The notes then came back WRONG, caused by my own clause: 1/3 written in the LEARNER'S voice ("Ở câu này tôi
  đã tự nghi ngờ bản thân") and 2/3 describing this turn rather than a habit. `PRACTICE_PROTOCOL` is written
  in the learner's first person, so a clause saying "something about ME" inherited that voice. After naming
  the voice + durability: **3/3 fire as "Bạn …", 0 first-person, 0 turn-scoped, and rarity holds at 0 notes
  across 5 ordinary turns** (30 graded sentences, 60 review rows). K criteria 1–3 pass.
- **Scenario F: criterion 3 tested for the first time** (fixture now carries the WHOLE `practice` prompt — the focus
  menu lives in `PRACTICE_PROTOCOL`, so a `MODE_DISPATCH`-only fixture could never reach it). Round 1 exposed a real
  ordering ambiguity in `MODE_DISPATCH` step 1: 1/3 withheld the focus menu waiting for the clean-up yes/no. Fixed →
  0/3 withheld but 1/3 rewrote the verbatim line. Tightened → **3/3 on all five criteria**.
- Side finding, fixed: one trial greeted the learner with an emoji. Invariant #6 is unit-tested for the app's own
  text but the tutor had never been told, so `MODE_DISPATCH` now says it — and `lib/no-emoji.test.ts` promptly
  failed the build on the example emoji inside that very clause.
- Harness defect #5, mine: the first wrapper told trials to treat a file as their system prompt and emit tool calls
  that would not run. One trial correctly refused it as a request to fabricate tool output. Re-framed in the
  hypothetical ("write what you WOULD do") and it ran.

- **Then the supervisor ran the LIVE half of Scenario A — and it FAILED.** Real Claude Desktop, blank chat,
  the exact eval question: Claude answers from its own knowledge and never calls `check_library`.
  Mid-session, protocol loaded, it does. So the tool and the protocol work; what fails is exactly the case
  the imperative tool descriptions exist to cover.
- Re-ran the subagent half with a deliberately NEUTRAL prompt (the original said "if you would call a tool,
  output the call … then stop", which makes a tool call the only well-formed output — it measured WHICH
  tool, not WHETHER). Neutral version: still **5/5**. So the wording was not the cause. **A subagent handed
  ~64k of imperative tool descriptions as CONVERSATION TEXT over-predicts tool use whatever you ask it** —
  Scenario A's subagent half is VOID, not merely optimistic, and it is the defect that produced the
  flagship GREEN rather than a false red.
- Shipped the fallback the plan pre-wrote: a Claude Desktop **Project Instructions** block
  (`CLAUDE_PROJECT_INSTRUCTIONS`), narrated in the `/guide` connect step as required setup, not a tip.
  Recorded as UNMEASURED — the same standard that just voided its predecessor.
- Decided Scenario D: **accept 3/4, do NOT build server-side ratchet priming.** The ratchet lives inside a
  `check_library` result, and the live test says that call does not happen in a blank chat — priming would
  tighten a path the learner never enters. Revisit once the lookup actually fires there.
