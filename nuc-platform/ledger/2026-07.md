### 2026-07-28 — Restating a rule does not make it stick; restructuring so compliance is the easy path does

<a id="2026-07-28-restating-a-rule-does-not-stick-restructuring-does"></a>

**Restating a rule does not make it stick; restructuring so that the compliant action is the path of least resistance
does.** First measured claim on this platform — every prior improvement was justified by argument alone.

**Setup.** The ledger's own header carried "one line per lesson + a pointer" from 2026-06-12 and was violated for 203
consecutive entries, some over 2500 characters, until the file hit 421KB. On 2026-07-28 two things changed together: the
rule was restated as an explicit two-write procedure, *and* the file was split so a `ledger/YYYY-MM.md` exists to append
detail to and the index table has a `Detail` column that wants a link.

**Method** (`.claude/scripts/eval-ledger-rule.mjs`, per `/behavioural-eval`). Two arms differing in one variable — the
exact pre- and post-change governance bytes. Two fixtures chosen to fail for different reasons: a SHORT lesson (little
pressure to over-write) and a LONG one (the shape that produced the fat rows). Metric counted from the files the model
actually edited — index-row length in characters, and whether a detail entry appeared. No judge, no self-report.
3 independent runs × 4 cells.

**Result.** Control index rows: 340 / 380 / 428 chars (short) and 560 / 601 / 738 (long) — every one pastes the
reasoning into the index, exactly the historical failure. Treatment: 189 / 189 / 189 and 156 / 164 / 199, with a
correctly anchored detail entry every time. Direction unambiguous; n is small, so read it as direction, not effect size.

**Two harness defects, found by suspecting the instrument before believing a clean result** — worth more than the pass
rate, because they are the reason to trust the third run:
1. **Fixture leak.** An empty `ledger/` directory was created for *both* arms, showing the control model the structure
   under test. One control run duly split its entry into it. Control now gets the world it actually had.
2. **False negative.** `detailWritten` only looked for `2026-07.md`, so a control run that wrote
   `2026-07-28-green-ci-not-deployed.md` scored `false` — flattering the treatment arm.
Both were fixed before the reported run; the direction survived the correction (control rows got *longer*, not shorter).

**What this refines.** "Enforce a rule with a gate, don't just document it" stays right about *documentation*, but the
gate is not the only escalation. Here **structure** did the work: prose alone (control) had carried the same intent for
six weeks and failed, while the same intent plus a place to put the detail succeeded on every trial. Prefer, in order:
(1) make the compliant path the obvious one, (2) measure it, (3) add a gate only if the measurement says prose lost. A
gate that duplicates good structure is machinery for its own sake. See
[[2026-07-28-building-beside-the-harness-instead-of-on-it]].

### 2026-07-28 — Building BESIDE the harness instead of ON it is how good work becomes waste

<a id="2026-07-28-building-beside-the-harness-instead-of-on-it"></a>

**Building BESIDE the harness instead of ON it is how good work becomes waste — the capability you are hand-rolling may
be on the vendor's roadmap.** Over ~6 sessions (2026-06-14 → 06-20) the platform built `auto-pilot`: a dumb external
orchestrator relaunching a fresh `claude -p` per batch, a scheduled Windows-Task wrapper, and a two-way Discord control
plane with RS256-signed single-use approval tokens synced through a private git repo. It was well-engineered and
genuinely worked (B5 passed: 3 fresh-context batches, phone-approved gate crossing, zero T4 crossed). On 2026-07-28 all
of it was deleted, because Claude Code now ships **scheduled cloud agents (`/schedule`) and remote agent execution**
natively — the same capability, maintained by the vendor. Corroborating detail: the control plane was already dead on
the Linux box (no gates clone, no state dir, no timer) because it had been built Windows-first and never ported; nobody
noticed, which is itself the tell that it had stopped earning its keep.

**Why it happened.** The work was never re-checked against the platform it was extending. There was no trigger that
asked "did the harness just ship this?" — only a roadmap that kept executing. Nothing in the process was *wrong*:
research-before-design ran, the gate was exhaustively tested, propose-don't-execute held throughout. Good process on a
premise that silently expired.

**What to do instead.** ① Before building infrastructure, read the **official docs and changelog of the tool you are
running inside** — cheap and boring, and on 2026-07-28 that source (`code.claude.com/docs/en/memory`) beat 40 scouted
third-party sources for value. "Standing on the shoulders of giants" usually means the giant you are already standing
on. ② Add a **release trigger**: on a harness version bump, diff the changelog with exactly one question — "does this
replace something we hand-rolled?" ③ Prefer extending the harness's own mechanism over a parallel one (the same session
moved agent memory onto native auto-memory rails for this reason, gaining enforced caps for free).

**What survived, and the distinction that matters.** Deleting the orchestrator is not deleting the *safety* layer.
`autonomy-gate.mjs` (T1–T4 tiers + the self-governance write ban, the CVE-2025-53773 lesson) was kept, simplified from
255 → ~135 lines by dropping the now-meaningless signed-release path, and its rewritten suite went 34 → **67 cases** —
which immediately found a real hole: the gate claimed fail-closed but the shared lenient payload parser let a malformed
payload through as "allow". **Retiring a feature is a good moment to test what is left, because the removal changes
what the survivors are load-bearing for.** Residual open risk, documented in `09-autonomy-contract.md`: the gate's
`CLAUDE_AUTONOMOUS=1` trigger was set by the retired orchestrator, so **nothing sets it today** — a native remote run
may be ungated. Verify empirically before trusting it.

### 2026-07-13 — To let users DELETE an entity that owns append-only logs WITHOUT violating "logs are never deleted": make the log's FK…

<a id="2026-07-13-to-let-users-delete-an-entity-that-owns-append-only-logs-wi"></a>
