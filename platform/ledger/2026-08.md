### 2026-08-01 — A metric that cannot move must never be printed as a measurement

<a id="2026-08-01-a-metric-that-cannot-move-must-never-be-printed-as-a-measurement"></a>

**A metric that cannot move must never be printed as a measurement.** `usage-census` reported, per hook, `ran`
(how often it executed) and `fired` (how often it exited 2), and its own comment read *"ran>0 with fired=0 over
weeks is the signature of a guard that costs time and catches nothing"*. The audit plan turned that into a target:
*"≥1 firing each, or justify the hook"*.

Measured 2026-08-01 against 2,874 real log events: **7 of the 15 installed hooks have no `process.exit(2)` path
anywhere in their source.** They speak by printing `hookSpecificOutput.additionalContext` or a `systemMessage` and
exiting 0 (`plan-checkin`, `compact-recap`, `tree-moved-notice`, `git-sync-check`, `memory-wiring-check`,
`harness-drift-check`), or they have no speech at all and work by side effect (`prettier-on-edit`). For every one
of them, `fired = 0` is true **by construction and forever**. The instrument was nominating seven working hooks for
retirement using a number that is physically incapable of being anything else.

**The general form, and it is sharper than "beware a wrong metric":** before reading a zero as a finding, ask
whether the thing being counted is *reachable at all* for the subject being judged. A wrong number can be fixed by
measuring again; an unreachable one returns the same answer forever and gets more convincing every week it is
re-observed. This is the same shape as `[→ 2026-07-27 "A control arm can be confounded into always agreeing"]` and
its 2026-07-31 addendum — a null is only a null when the success path was reachable — arriving through a completely
different door: there it was an experiment, here a dashboard column.

**The fix, and why it is shaped this way.** `fired` is now `null` → printed `n/a` for a hook with no exit-2 path,
derived by scanning that hook's own source with comments stripped, **never from a list of names** — so a hook added
tomorrow classifies itself, and `tree-moved-notice`, which *discusses* exit 2 in its header, is not miscounted as
able to use it. It also had to be made to survive `--json`: `platform-report` re-created the whole bug on the far
side of the pipe with `r.fired ?? 0`, in the one document the supervisor is told to audit the agent's judgement
with, and that render path had **no test at all** until this was found.

**What is still not answerable, and it needs a human.** Whether an advisory hook has ever actually *said* anything
requires recording a `spoke` flag in `.claude/hooks/_util.mjs` — governance, which the agent never edits. Proposal:
`platform/proposals/2026-08-01-hook-spoke-flag.md`. Until then `compact-recap` (5 runs) and `harness-drift-check`
(9 runs) are hooks whose entire value is what they print, and whether they have ever printed is unknown.

**Check left behind:** the two readers now carry it, with 2 new cases + 2 mutants in `usage-census.test.mjs` and a
new case in `platform-report.test.mjs` proven red by reverting the fix.

**Forward pointer, 2026-08-01 (not a rewrite — this file is append-only and records what was true when written):**
the `spoke` flag SHIPPED later the same day, so the paragraph above about it being unanswerable is now history.
How it got there is its own lesson → `[→ 2026-08-01 "A blocked edit is evidence about the edit"]`.

### 2026-08-01 — A finding whose remedy is "ask a human" needs a HIGHER verification bar, not a lower one

<a id="2026-08-01-a-finding-whose-remedy-is-ask-a-human-needs-a-higher-bar"></a>

**A finding whose remedy is "ask a human" needs a higher verification bar than one whose remedy is code.** The
second-brain audit closed with one item explicitly labelled *"One contradiction needing a human decision, not an
agent guess"*: `platform/skill-proposals/prisma-expert-migration-rehearsal.md` said `status: installed`, but no
skill directory of that name existed.

There was no contradiction. The file's second line says *"NOT a new skill — a section to paste into
`.claude/skills/prisma-expert/SKILL.md`"*, its frontmatter says `kind: extension` and `extends: prisma-expert`, and
the content **is** installed, at `SKILL.md:79`. The audit had matched the proposal's `proposed_name` against the
skill directories and read the absence as a defect. No tool does this — it was the agent's own inference, so
nothing needed retuning, only deleting.

**Why this class is worse than an ordinary false finding.** A wrong code finding is caught by the next test run,
for free. A wrong escalation is caught by *the supervisor*, using the one resource that does not scale and cannot
be recovered — and this one sat for two days with a label that guaranteed a turn would be spent on it, to be told
the plan had misread one of its own files. The asymmetry runs the opposite way to intuition: "I'm not sure, so I'll
ask a human" **feels** like the cautious move, and it is the move that spends someone else's attention on the
agent's uncertainty.

**What to do instead:** before writing "needs a human decision", read every file the claim mentions, end to end,
and state what was read. If the contradiction survives that, it is real and worth the turn. Related:
`[→ 2026-07-30 "An automated dead-weight list, run over a knowledge base, is wrong ~97% of the time"]` — same
audit, same failure to check a confident-looking absence, but that one was the tool's and this one was the agent's.

**No mechanical check is possible, and this is the legitimate case for saying so:** whether a claim was verified
before being escalated is a property of the reasoning, not of the repo. What replaces a detector here is that the
audit plan now carries the withdrawal in full, next to the finding it retracts, so the next reader of that section
sees the correction and the cost together rather than a tidy deletion.

### 2026-08-01 — A tool with no config does not do nothing; it applies its own defaults

<a id="2026-08-01-a-tool-with-no-config-does-not-do-nothing"></a>

**A tool with no config does not do nothing — it applies its own defaults, silently and confidently.** The `fleet`
control plane has no root `.prettierrc` on purpose: `.claude/**` is hand-wrapped at ~110 columns and `platform/**`
is prose whose line breaks carry meaning. Running `npx prettier --check` on four edited scripts reported all four
non-conforming, which looks exactly like a lint failure to fix — so `--write` was run. Prettier fell back to
**printWidth 80** and reflowed everything, turning a 200-line semantic diff into **680 lines**, most of it
re-wrapping code the change never touched. Recovery was `git checkout --` to HEAD and re-applying all eighteen
edits by hand.

Two things made it worse than a formatting accident. First, the probe used to decide whether the files were
*already* non-conforming copied them to `/tmp` and checked there — **outside the repo, therefore under a different
config resolution**, so it answered a question about a different file and returned a reassuring 0. Second, the
false red is *inviting*: a tool reporting hundreds of violations does not read as "wrong tool", it reads as "work
to do", and the destructive fix is one flag away.

**Second occurrence, so it leaves a guard rather than a note.** The same mechanism was recorded 2026-07-29 from the
opposite direction — `rulebook` Step 1.2: a new project with no `.prettierrc` had Prettier *"silently use its own
defaults"*. The guard is a root **`.prettierignore`** listing `.claude/`, `platform/`, `CLAUDE.md`,
`CLAUDE.local.md`, verified to be honoured **even for explicitly-passed paths**, so `npx prettier --write
.claude/scripts/x.mjs` is now a no-op and `--check` reports clean instead of manufacturing the false red. It is
allowlisted in `.gitignore` (`!/.prettierignore`) — this repo ignores `/*` by design, and an un-tracked guard
protects one machine while the other keeps walking into it. The sibling repos are deliberately **not** listed:
each has its own `.prettierrc`, Prettier resolves config per file, and those files really are Prettier-managed.

**The generalisation worth keeping:** when a tool's output disagrees with a repo's visible convention, the first
hypothesis is that the tool is not reading the repo's config — not that the repo is wrong. And a check performed
on a copy outside the tree is not a check of the tree.

### 2026-08-01 — Addendum to [2026-07-24, "a regex lint gate must match CLASS TOKENS … and STRIP comments"]

<a id="2026-08-01-addendum-prose-about-a-pattern-matches-the-pattern"></a>

**You cannot spell a pattern out inside the file that searches for it.** The 2026-07-24 entry recorded this for
product-level regex gates in `sakubun` (an import path matching a bare `truncate`; an apostrophe in a `// don't`
comment forming a bogus string literal). On **2026-08-01 the same mechanism hit platform tooling six times in one
day**, so this is an addendum and a **detector**, not a fourth write-up — the lesson was already correct and
already written.

The six, each *text ABOUT a thing mistaken for the thing*:

1. `usage-census` counted a document that **discusses** `INSTALL.md` as depending on it.
2. `canBlock` read a comment **about** `exit 2` as an exit-2 path — `tree-moved-notice` discusses it in its header.
3. `claude-md-budget` accepted the sentence **explaining** a missing governance surface as that surface being
   named: `agents/` was deleted from the list and the check still passed.
4. `_layout`'s no-hardcoding assertion failed on the comment written to explain that nothing was hardcoded.
5. **The detector for this failure matched its own source**, because its pattern contained the bare identifier.
6. **Then it matched its own explanation of fix 5**, because that sentence wrote the invocation form out
   literally, parenthesis included.

Five and six are the useful ones: the pattern survives two deliberate attempts to document its own repair. The
fix both times was to change the PROSE — describe the shape in words — never to exempt the file (an exemption
blinds the detector to the real thing later) and never to weaken the pattern (that blinds it immediately).
`claude-md-budget` had already reached this independently and shipped a convention for it: write the citation
form with angle brackets so the scanner cannot match its own documentation.

**Why the obvious guard was rejected, with the number.** "Every tool that pattern-matches file contents needs a
comment case" **matches 26 tools** — a detector that fires on day one is mistuned, not insightful. It is also
simply wrong: `tool-catalog` reads `@vi` metadata *out of* comments by design, and `claude-md-budget`'s citation
scan deliberately reads them too. **"Always strip comments" is not the rule.** Knowing which side of the line you
are on is, and no pattern can infer intent.

**Check left behind — `recurrence-check` D8, `comment-stripper-with-no-comment-case`.** A tool that has *decided*
comments are noise, and blanks them, must have a test where the pattern appears only in a comment. Narrow on
purpose: it guards the four fixes against silent removal — the real recurrence risk now — and grows by itself as
more tools strip. Keyed on the TEST like D7, so the claim is something somebody runs rather than a sentence in a
header. Shipped at **0 firing**, proven red by replacing the word "comment" in one suite, and its own suite pins
both directions including the bare-mention case that fired twice.

### 2026-08-01 — A blocked edit is evidence about the edit

<a id="2026-08-01-a-blocked-edit-is-evidence-about-the-edit"></a>

**When a guard refuses an edit, the first hypothesis is that the edit is wrong — not that the guard is in the
way.** The `spoke` flag needed one boolean recorded per hook run. The implementation wrapped
`process.stdout.write` and `process.stderr.write` inside `recordRun()`. The permission layer refused it, twice,
across two separate sessions of asking.

The tempting readings were both wrong: *"the classifier is over-broad"* and *"`.claude/hooks/**` is simply
blocked"* — the second was disproved by a patch to `autonomy-gate.mjs`, a neighbouring file in the same
directory, going through minutes earlier. That left the actual question: **what is different about this edit?**

A hook that runs on every tool call and monkey-patches stdio is, from the outside, indistinguishable from one
that tampers with or exfiltrates what it sees. That is a correct thing to refuse, and the author had not noticed
he was writing it.

**What shipped is strictly better.** `process.stdout.bytesWritten` is a counter the stream already maintains, so
the output is *observed* without being touched — it cannot see content even in principle. Two lines instead of
nine, verified across five output modes on piped stdio before being relied on (silent `0/0`, a stdout write `30`,
a stderr write `9`, `console.log` `16`, a bare newline `1`), then proven end to end with the same hook giving
both answers.

**The general rule, and it applies to every gate on this platform:** a refusal carries information. Routing
around it — a different tool, a shell redirect, a bigger permission — discards that information at exactly the
moment it is most valuable. Ask what the guard can see that you cannot, and the answer is sometimes a better
design. Corollary, from the same day: `_util.test.mjs` pinned the log's field set as CLOSED for privacy reasons
and **failed the moment the new field shipped** — which is what that assertion is for. A field has to be argued
into a closed set, and `spoke` qualifies only because a boolean derived from a byte count cannot carry content.

### 2026-08-01 — A second front end is cheap only if the surface it drives is DATA

<a id="2026-08-01-a-second-front-end-is-cheap-only-if-the-surface-is-data"></a>

**Adding a whole second interface to an app cost almost nothing new — because the interface was generated from a
list, not written against one.** `sakubun` grew a terminal surface (a full-screen keyboard UI plus scriptable
commands) covering its management half. The client contains **no list of what commands exist**: the server declares
them once (`lib/cli/registry.ts` — name, group, Vietnamese summary, flags, writes-or-not), serves that list at
`GET /api/cli`, and the client builds its `--help`, its flag parsing and its screens from the response. The in-app
`/guide` reference table renders the same list. One array, three consumers — and a command added server-side is
reachable from all three with no client release.

This is the same move `lib/mcp/catalog.ts` already made for the Claude-facing surface, which is why it was the
obvious shape here: **the second use of a pattern is where you find out it was a pattern.**

**The tax it comes with, stated plainly, because it bit on the second command.** A served catalog needs a
human-readable face (flag names, help text, closed value sets) and the server needs a validator (zod). Those are
**two descriptions of one input**, and zod v3 cannot emit a JSON schema to derive the first from the second. Kept in
step by discipline, they lasted exactly one command: a renamed schema key left a flag that silently stopped working
and reported a key the user had never typed. The fix is a test pairing them — every declared flag maps to a real
schema key, every schema key has a flag (an input nobody can send is dead), `required` agrees, and a choice list
equals the schema's enum. Verified by mutation, not by hope: renaming one param fails naming the command and flag.

**Generalisation for any project here.** If you are about to give an app a second front end — a bot, a CLI, an MCP
server, a webhook console — the question is not "how much UI work is it" but **"is the surface declared as data
yet?"** If yes, the front end is a renderer. If no, you are about to write the surface a second time, and the copies
will diverge. Also reuse the credential you already have: this surface authenticates with the app's existing
per-user bearer token, so revoking it closes every machine surface at once instead of leaving one behind.

### 2026-08-01 — Measure the requirement before you refuse the dependency

<a id="2026-08-01-measure-the-requirement-before-you-refuse-the-dependency"></a>

**This fleet is biased against dependencies, and the bias is usually right — which is exactly why overruling it
needs a measurement.** `lib/env.ts` refused `@t3-oss/env-nextjs` for ~90 lines of zod; `commitlint`+`husky` were
refused because the platform's own git hooks already worked. So the default answer for a terminal UI was
"hand-roll the ANSI, like `mcp-lab-client.mjs` and `ui-audit.mjs` already do, zero dependencies".

That answer was wrong, and one line of measurement showed it: `'ばかりに'.length` is **4**; its terminal width is
**8**. Japanese is double-width, so every column pad, every truncation and every box border in a hand-rolled table
is wrong on almost every row of this app's content. Getting it right means implementing East Asian Width — which is
`string-width`, and that is where the candidate library's dependency tree comes from in the first place. So `ink`
was adopted (MIT, node >= 22, react >= 19.2 which the app already had), under two conditions that kept the cost
honest: **no JSX**, so the client stays plain `.mjs` runnable with `node` and needs no build step; and
**devDependency**, so it never reaches the runtime image.

**The general form:** "we don't take dependencies for that" is a prior, not a finding. Before applying it, name the
REQUIREMENT and ask whether the hand-rolled version would have to re-implement the library. When the answer is yes,
refusing the dependency does not avoid the code — it makes it yours, untested, and yours to get wrong. The
symmetric-evidence rule applies to this fleet's own habits too, not only to the community's.

### 2026-08-01 — A plan can be stale on the day it is written, because a long plan quotes an earlier artefact and then stops re-reading it

<a id="2026-08-01-a-plan-can-be-stale-on-the-day-it-is-written"></a>

**A plan can be stale on the day it is written.** The harness-upgrade plan was drafted 2026-07-31 from the rows of
`harness-reexamination` — while that sibling plan was *retracting several of those rows in the same session*. It then
reached the supervisor as the thing to execute. Reconciled against the repo on 2026-08-01, **eight of its steps were
dead on arrival**: three described work already shipped, three rested on premises the sibling had refuted, and two
targeted mechanisms that no longer exist. One was worse than dead: step 2.2 said to put `allowed-tools` on the
read-only skills "so `/host-audit` can keep its report-only promise" — and `allowed-tools` **grants** permission, so
executing it would have pre-approved the three skills that touch auth and secrets.

**The mechanism is not carelessness, and naming it correctly is the whole value here.** Every quotation in the plan was
accurate at the moment it was copied. What failed is that a long document *freezes* its sources: the citation is written
once, the source keeps moving, and nothing in the writing process re-reads it. That is why "be more careful" is not the
fix and why the four instances of *researching a solved problem* in this plan family (A3, L1, L2, and F-new-1) all have
the same shape — the repo already contained the disproof, in a file nobody opened.

**F-new-1 is the sharpest instance, because of its direction.** The plan's self-declared headline finding was that fleet
runs two memory systems and governs only one — an uncommitted, self-written instruction file loading into every session,
unreviewed. Measured: `~/.claude/projects/C--project-fleet/memory/` does not exist, `autoMemoryDirectory` points at the
**committed** tier, and `.claude/hooks/memory-wiring-check.mjs` verifies that wiring at every session start across all
three settings layers. fleet did not merely avoid the second system; it redirected the vendor's rails at its own
directory and wrote a hook to prove it. **The finding accused fleet of the exact sin fleet is organised around, and the
disproof was a hook file in the same directory.** A finding that flatters the finder needs the same evidence bar as one
that costs him — the symmetric-evidence rule, pointed inward.

**The inversion this produced, which matters more than any single correction.** R3 asked to "cut the tumours". Of the
three named candidates, **two were already retired** (the PowerShell orchestrator, gone; the zero-consumer MCP server,
re-targeted to a plugin hook with "nothing left to build" recorded) and a third defect class — 10 of 38 unparseable skill
frontmatters — was already fixed. So the honest reading is the opposite of the complaint that motivated the plan: fleet
has been cutting, and what felt like a backlog was **finished work nobody had counted.** That relocates the problem from
sprawl to legibility, which is `idea-0025`'s territory, not a cleanup's.

**What to do instead of remembering this.** Every plan past `draft` now carries `## Before executing a batch`, and its
first question is no longer "does it already exist?" but **"does it already exist — checked against the `related:`
plans' CURRENT text, not the text this plan quoted?"** `eval-plan-execution-gate` measured that block on the
duplicate-work failure (control 5/5 built the duplicate, treatment 0/5), so it is a mechanism with evidence rather than
a resolution. Candidate check, not built: `plan-audit` could flag a step that cites a struck-through or retracted row in
a `related:` plan.

### 2026-08-01 — Shipping the prevention makes latent bugs reachable: the first real use of a mechanism is a test nobody wrote

<a id="2026-08-01-shipping-the-prevention-makes-latent-bugs-reachable"></a>

**Shipping `.worktreeinclude` — eight lines of configuration — immediately exposed two defects that had been sitting
there, harmless only because nothing exercised them.**

The file exists because `user-edits-files-concurrently` is a named, repeated failure and fleet's answer was a *detector*
(`tree-moved-notice.mjs`, which fired again that very day). Isolation is the *prevention*. Both are cheap; prevention
outranks detection.

**Defect 1 — the file was silently gitignored.** This repo's `.gitignore` ignores everything at the root (`/*`) and
allowlists back a handful of paths. A new root dotfile is therefore invisible **by default**: `git status` never mentions
it, and it would have existed on one machine only — which for a file whose entire job is to make a *second* checkout
work correctly is a total failure. This is the second occurrence of the identical trap; the first
(`.prettierignore`) is documented in `.gitignore` itself with the reason. The allowlist entry now carries both.

**Defect 2 — the memory guard gave a FALSE WARNING inside a worktree, and it is the fifth checker to do so.**
`memory-wiring-check` compares `autoMemoryDirectory` against *this* tree's `.claude/memory`. In a worktree that
inherits the setting — which is exactly what `.worktreeinclude` now guarantees — the path points at the **main** tree,
which is correct and is the whole point of one shared tier. The hook called it a problem: *"the git-synced shared tier
is not being loaded or written to."* Every worktree session would have opened by telling the agent it had no memory of
the user, and this hook's `additionalContext` instructs the agent to pass that on to them. Fixed by reusing
`_layout.mjs`'s `worktreeInfo` rather than re-deriving it, with the import dynamic and swallowed so a SessionStart hook
can never be the reason a session will not start.

**The general form.** A mechanism that nothing uses is not "working" — it is *unmeasured*. Four checkers were fixed for
the worktree blind spot on 2026-07-31 by auditing which ones read sibling repos; the fifth was missed because nobody
asked what happens to *memory* in a worktree, and nobody asked because no worktree was ever usable. So: **when you ship
the thing that makes a path reachable, budget for finding bugs on that path in the same session** — and verify by
running it, not by reading the flag. Both defects were found in the first two minutes of a real `claude --worktree`
run; neither was visible in the diff.

**Test discipline that came with it.** The suite now builds a **real** `git worktree` (its sibling `_layout.test.mjs`
injects a fake `spawn` and says why), because the bug was invisible to every fake: the hook derives its repo root from
its own file location, so only a genuine second checkout puts a different root under it. And an existing mutant went
stale on the same edit — anchored to the line the fix replaced — so it changed nothing and the suite died on its own
staleness assertion. That assertion is the reason this was a ten-second fix instead of a false green: **anchor a
mutation on the smallest text that identifies the mechanism, never on a line likely to be rewritten around it.**

### 2026-08-01 — If a human is the only way to reach a line, no gate covers it: make the human an argument

<a id="2026-08-01-if-a-human-is-the-only-way-to-reach-a-line-make-the-human-an-argument"></a>

**A feature passed every gate this platform has and was broken for the user on the first try.** `sakubun login`
died on its opening prompt with `Cannot read properties of undefined (reading 'trim')`: the code imported
`createInterface` from **`node:readline`**, whose `rl.question(query, cb)` is a callback function returning
`undefined`, so `await rl.question(q)` was `undefined`. The promise-returning `question` is in a different
module, `node:readline/promises`. Nothing complains — same name, same shape, plain `.mjs`, no lint rule.

At the moment it shipped: 667 tests green, lint clean, typecheck clean, build clean, image rebuilt, container
healthy, and a dozen commands verified end-to-end against a live server. All true, all irrelevant to that line.

**The part worth generalising is not "test more" — it is WHY the gate set was structurally blind.** The prompts
read `process.stdin` directly, so the only entry point was a person at a keyboard. And the one test that touched
the area — "refuses politely when there is no TTY" — **passed by never reaching the bug**: the TTY guard throws
before `createInterface` is called, so the non-TTY path exercised the guard and skipped everything after it. A
test that passes by not arriving is worse than no test, because the green reads as coverage. (Same shape as
`[→ 2026-08-01 "A metric that cannot move must never be printed as a measurement"]`: the instrument could only
ever return one answer.)

**The remedy is a design rule.** Any path whose sole entry point is a human — a prompt, a keypress, an OAuth
redirect, a file drop — must take that human as a PARAMETER: pass the streams, pass the clock, pass the event.
Concretely here: `ask`/`askHidden`/`confirm` now take `{ input, output }` (defaulting to the process's), the
login flow moved out of the entry file into its own module with its collaborators injectable and a
`{ ok, error }` return instead of an `exit`, and 13 tests drive the whole sequence with neither a terminal nor a
server. The load-bearing assertion is `expect(typeof answer).toBe('string')` — it fails for the entire class of
"awaited a callback API", not for one line.

**The uncomfortable detail, kept because it is the actual lesson.** The technique was ALREADY in the same
codebase, one directory away: the terminal UI is tested by handing the real component tree a stub stdin/stdout.
The prompts simply did not get the same treatment. So the failure was not ignorance of how to test it — it was not
asking "who is the only caller of this?" while writing it. That question is cheap and it is the whole gate.

**Corollary for anything shipped inside a container image:** a green test run says nothing about the running
artefact. The fix was re-verified by executing the prompts INSIDE the container against fake TTY streams before
being called done.

**Same family, found independently the same day — and it already HAS a detector.** A concurrent session
recorded `eval-with-no-reachability-assertion` in `.claude/scripts/recurrence-check.mjs` (learned 2026-08-01): *an
eval never asserts that its own success path is reachable, so a null may be an artefact.* That is this lesson's
sibling — both are **a check that passes because it never arrives at the thing it claims to cover**. Two
occurrences in one day, in two unrelated parts of the fleet, is the signal that this is a shape rather than an
accident.

**Why no new detector here, stated rather than defaulted to** (`/session-wrap` Step 4b's third option is
legitimate but must be argued): the existing detector is scoped to `.claude/scripts/eval-*.mjs`, and the
generalisation — "a test whose only assertion is that a GUARD fired, in a file whose subject is the code after the
guard" — needs semantics no regex has. What *is* mechanically catchable is the narrow footgun (`node:readline`
imported without `/promises` in a file that awaits `.question(`), and that is one occurrence in one project,
where `cli/lib/prompt.test.mjs` now guards regressions at the project level. **Widening the eval detector to
"any check that asserts only a guard" is the open candidate**, and it is deliberately left to whoever owns that
